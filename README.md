# MTS_kubernetes
# Автоматизированная инфраструктура веб-приложения в Kubernetes (v1.37)

Данный репозиторий содержит полностью автоматизированное, идемпотентное решение для развертывания веб-приложения в Kubernetes, его публикации через современные стандарты **Gateway API (Envoy Gateway)**, а также комплексного сбора логов (**Filebeat**) и метрик (**Prometheus**).

---

## 🛠 Технологический стек и версии

*   **Операционная система:** Ubuntu 24.04 LTS
*   **Оркестрация кластера:** Kubernetes v1.37.0 (развернут с нуля через `kubeadm`)
*   **Рантайм контейнеризации:** containerd v1.7.x (Cgroup driver: `systemd`)
*   **Сетевой плагин (CNI):** Flannel (актуальный релиз, адаптирован под CIDR )
*   **Публикация (Gateway API):** Envoy Gateway v1.6.1 (Ресурсы: `GatewayClass`, `Gateway`, `HTTPRoute`)
*   **Мониторинг:** Prometheus Operator (`kube-prometheus-stack` via Helm)
*   **Логирование:** Elastic Filebeat (развернут как `DaemonSet` для сбора контейнерных логов)
*   **Пакетный менеджер:** Helm v4

---

## 🏗 Требования к среде

Для успешного запуска скрипта и развертывания решения необходима:
1. Виртуальная машина или физический сервер с чистой установкой **Ubuntu 24.04 LTS**.
2. Права суперпользователя (`sudo`) у запускающего скрипт пользователя.
3. Доступ к Интернету для скачивания пакетов, Helm-чартов и Docker-образов.

---

## 🚀 Пошаговая инструкция по развертыванию

Развертывание полностью автоматизировано и сведено к выполнению одного сценария. Скрипт является **идемпотентным** — его повторный запуск безопасно сбрасывает кластер в исходное состояние и накатывает конфигурацию заново.

1. Склонируйте репозиторий на целевую машину под управлением Ubuntu 24.04:
   ```bash
   git clone https://github.com/zx4falll/MTS_kubernetes.git
   cd <ИМЯ_ДИРЕКТОРИИ>
   ```

2. Сделайте скрипт развертывания исполняемым и запустите его:
   ```bash
   chmod +x deploy.sh
   sudo ./deploy.sh
   ```

*Что произойдет во время работы скрипта:*
* Устранятся возможные блокировки пакетного менеджера APT (`unattended-upgrades`).
* Сбросится старый кластер (если он был) и очистятся остаточные конфигурационные файлы.
* Настроятся параметры ядра Linux (`br_netfilter`, `ip_forward`) и отключится SWAP.
* Установится и настроится контейнерный рантайм `containerd` с драйвером `systemd`.
* С нуля инициализируется кластер `kubeadm` (v1.37), снимутся taints с master-ноды для работы в режиме Single-node.
* Развернутся Flannel CNI, CRD Gateway API v1.6.1 и Envoy Gateway.
* Будет развернуто демонстрационное веб-приложение, Prometheus (через Helm) и Filebeat.

## 🔍 Инструкции по проверке компонентов решения

### 1. Проверка доступности приложения через Gateway API
Доступ к приложению организован через Envoy Gateway, который запатчен в тип `NodePort` на порт **30080** для детерминированного доступа на локальной машине.

Выполните HTTP-запрос к шлюзу:
```bash
curl -i http://localhost:30080/
```
**Ожидаемый результат:**
* HTTP-код ответа: `200 OK`
* Тело ответа содержит однозначно проверяемую строку: `Hello World!`

### 2. Проверка работы Мониторинга (Prometheus)
Prometheus развернут в составе оператора внутри пространства имен `monitoring`. Он собирает метрики со всех базовых компонентов инфраструктуры (Kubelet, CoreDNS, Envoy).

Для выполнения тестового запроса (Prometheus query) пробросьте порт к веб-интерфейсу Prometheus:
```bash
kubectl port-forward -n monitoring svc/monitoring-kube-prometheus-prometheus 9090:9090 --address 0.0.0.0 &
```
Откройте браузер по адресу `http://<IP_сервера>:9090` или выполните CLI-запрос к API Prometheus:
```bash
curl -s "http://localhost:9090/api/v1/query?query=up" | json_pp
```
**Ожидаемый результат:** Наличие доступных таргетов (со значением `1`), собираемых Prometheus в режиме реального времени.

### 3. Проверка логирования (Filebeat)
Агент Filebeat запущен как `DaemonSet` на ноде и собирает структурированные `access/error` логи демонстрационного веб-приложения напрямую из путей `/var/log/containers/*`.

1. Сгенерируйте несколько HTTP-запросов к приложению:
   ```bash
   curl http://localhost:30080/
   ```
2. Проверьте, что логи успешно захватываются агентом. Поскольку в рамках базового решения Filebeat пересылает логи в настроенный stdout/output (или локальный инстанс), убедитесь в наличии записей access-логов:
   ```bash
   kubectl logs -n default -l app=filebeat --tail=50 | grep -i "nginx"
   ```

## ✨ Реализованные дополнительные возможности (Улучшения)

1. **APT Lock-Fix & Полный сброс:** Скрипт развертывания решает частую проблему на Ubuntu — гонку за блокировку `dpkg/apt` с фоновыми обновлениями ОС, делая проверку экспертами бесшовной.
2. **Бесшовный сброс (Идемпотентность):** Скрипт автоматически выполняет `kubeadm reset` и чистит сетевые интерфейсы `cni0/flannel.1`, позволяя безопасно запускать деплой многократно.
3. **Advanced Gateway API (Envoy Gateway):** Вместо классического устаревшего Ingress-контроллера применена современная и производительная архитектура на базе Envoy Gateway со стандартными спецификациями Gateway API v1.6.1.
4. **NodePort Патчинг:** Сервис Envoy автоматически переводится скриптом в фиксированный NodePort (`30080`), гарантируя доступность шлюза без внешнего Cloud LoadBalancer.

---

## ⚠️ Известные ограничения
* Решение спроектировано под режим **Single-node** кластера (все компоненты запускаются на одной управляющей машине).
* Используется NodePort вместо полноценного External LoadBalancer, так как среда тестирования является изолированной локальной машиной на Ubuntu 24.04.
